# AI course creation: frontend integration report

## Purpose and scope

This document maps the creator-facing AI course flow to the Figma screens and
the backend API. It covers initial submission, the two progress phases,
cancellation, recovery, and navigation into the existing course builder.

Base path: `/api/v1`

Authentication: every endpoint in this flow requires a Course Creator JWT in
the `Authorization: Bearer <access-token>` header.

## Figma-to-API field mapping

| Figma label | Request field | Type | Rules |
| --- | --- | --- | --- |
| Course title | `title` | string | Required, maximum 255 characters |
| Description | `description` | string | Required |
| Course category | `category` | UUID | Required; must reference an active category |
| Topic | `topic` | UUID or `null` | Optional; must belong to `category` |
| Accept terms | `terms_accepted` | boolean | Must be `true` |
| Retry identity | `idempotency_key` | string | Recommended; reuse only for the same submission |

`course_title` remains accepted as a deprecated alias for `title`. New frontend
code must send `title`. If both are sent, their values must match.

Fields such as difficulty, learning objectives, tags, duration, modules,
lessons, and assessments are generated by the backend and displayed in the
builder after generation; they are not part of the initial request.

## End-to-end state flow

```text
AI title/details form
        |
        | POST /course-ai-generations/
        v
Creating content... (CREATING_CONTENT)
  1. Analyzing course objectives
  2. Generating course outlines
  3. Preparing course lessons, learning objectives etc
        |
        | course draft and outline persisted
        v
Preparing course details... (PREPARING_DETAILS)
  1. Analyzing course outlines
  2. Generating module information
  3. Generating course lessons, assessments, quizzes etc
        |
        | status = COMPLETED
        v
GET /courses/{course_id}/ -> existing Course Information builder screen
```

The backend makes one bounded provider request for the outline, one request per
module for lesson scripts and its module assessment, and one final-assessment
request. Lesson assessments are optional and are not generated by default.
The frontend follows the single-flight concurrency and time-limit rules below.

## Generation concurrency and time limits

A creator can have only one in-flight AI job at a time across course generation,
assist, and thumbnail work. A second request receives `429`; list and resume the
existing job rather than submitting again. Each `worker-ai` container has
concurrency `1`; the default Compose deployment runs one such container, so jobs
from different creators can be queued but only one AI task is actively executing
at once. Scaling the worker service enables cross-creator parallelism, subject
to the provider rate limit.

Celery task execution limits are per task attempt, not an end-to-end wall-clock
promise:

| Job kind | Soft time limit | Hard time limit |
| --- | ---: | ---: |
| Full-course generation | 30 minutes | 35 minutes |
| Assist or thumbnail | 5 minutes | 5 minutes 30 seconds |

The provider HTTP timeout is 180 seconds per request attempt, with bounded
provider and Celery retries. Rate-limit capacity waits, retries, and queue time
can extend the total job lifetime beyond one task limit; there is no strict
end-to-end generation SLA. Jobs with no heartbeat for six hours are treated as
stale and marked `FAILED` when a creator lists, polls, or starts another job;
that stale threshold is recovery cleanup, not a guaranteed six-hour completion
limit.

## 1. Start generation

Before creating a new job, call:

`GET /api/v1/course-ai-generations/`

By default this returns the caller's in-progress jobs: `QUEUED`, `RUNNING`,
and `STRUCTURE_READY`. Use this on page load to resume a previous loading
screen even when local storage was cleared or the user navigated away.

```json
{
  "status": true,
  "message": "Successfully retrieved data",
  "data": {
    "paginator": {
      "count": 1,
      "page": 1,
      "page_size": 10,
      "total_pages": 1,
      "next": null,
      "next_page_number": null,
      "previous": null,
      "previous_page_number": null
    },
    "results": [
      {
        "id": "<job-uuid>",
        "status": "RUNNING",
        "current_phase": "CREATING_CONTENT"
      }
    ]
  }
}
```

`GET /api/v1/course-ai-generations/?status=FAILED` lists failed jobs; replace
`FAILED` with any concrete generation status when a history view needs it.

`POST /api/v1/course-ai-generations/`

```json
{
  "title": "Practical Data Analysis for Beginners",
  "description": "Teach beginners to clean, analyze, and visualize realistic business data using spreadsheets and Python.",
  "category": "<category-uuid>",
  "topic": "<topic-uuid>",
  "terms_accepted": true,
  "idempotency_key": "ai-course-4b3f37c8"
}
```

The first accepted request returns `202`. Repeating the same request with the
same creator and `idempotency_key` returns the existing job with `200` and does
not queue duplicate work.

Important response fields:

```json
{
  "id": "<job-uuid>",
  "course": null,
  "kind": "FULL_COURSE",
  "status": "QUEUED",
  "stage": "",
      "current_phase": "CREATING_CONTENT",
      "celery_task_id": "<task-id>",
      "dispatch_attempts": 1,
      "retry_count": 0,
      "last_heartbeat_at": "2026-09-16T09:27:20Z",
      "result": {},
  "error_message": "",
  "cancel_requested": false,
  "builder_ready": false,
  "items": [
    {
      "key": "content_objectives",
      "label": "Analyzing course objectives",
      "phase": "CREATING_CONTENT",
      "status": "PENDING",
      "order": 0
    }
  ]
}
```

Persist the returned job `id` in route state and local storage. The job ID is
the recovery handle if the page reloads. Do not generate a new idempotency key
when retrying a request whose response was lost.

## 2. Stream generation progress (with polling fallback)

`GET /api/v1/course-ai-generations/{job_id}/stream/`

Prefer the authenticated SSE stream on the loading screens. The first `data:`
frame is a `snapshot` containing the full serialized generation job; subsequent
`progress` frames wrap the worker event at `payload.payload`. Each new connection
starts with a fresh snapshot, so it also recovers missed events after reconnecting.

Use `fetch()` with the Bearer token rather than native `EventSource`: browsers do
not let `EventSource` set the `Authorization` header. Never put the access token
in the URL. The endpoint responds with `Content-Type: text/event-stream`; it is
not a JSON envelope and should not be tested with Swagger Try it out.

```ts
type GenerationStreamMessage =
  | { event: "snapshot"; payload: GenerationJob }
  | { event: "progress"; payload: { job_id: string; payload: Record<string, unknown> } };

async function readGenerationStream(
  jobId: string,
  accessToken: string,
  signal: AbortSignal,
) {
  const response = await fetch(
    `/api/v1/course-ai-generations/${jobId}/stream/`,
    {
      headers: {
        Authorization: `Bearer ${accessToken}`,
        Accept: "text/event-stream",
      },
      signal,
    },
  );
  if (response.status === 404) throw new Error("Generation job not found");
  if (!response.ok || !response.body) throw new Error("SSE unavailable");

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  while (!signal.aborted) {
    const { value, done } = await reader.read();
    if (done) return;
    buffer += decoder.decode(value, { stream: true });
    const frames = buffer.split("\n\n");
    buffer = frames.pop() ?? "";
    for (const frame of frames) {
      const data = frame
        .split("\n")
        .filter((line) => line.startsWith("data:"))
        .map((line) => line.slice(5).trimStart())
        .join("\n");
      if (!data) continue; // Ignore keep-alive comment frames.
      const message = JSON.parse(data) as GenerationStreamMessage;
      if (message.event === "snapshot") renderJob(message.payload);
      if (message.event === "progress") applyProgressEvent(message.payload.payload);
    }
  }
}
```

Abort the stream when the loading screen unmounts. On unexpected close or
transient network failure, reconnect with bounded exponential backoff using the
same job ID; apply the new snapshot before processing progress again. On `401`,
refresh the session or route to login. If streaming is unavailable, fall back to
`GET /api/v1/course-ai-generations/{job_id}/` polling every two seconds. For both
transport paths, render only items whose `phase` equals `current_phase`, sort by
`order`, and drive icons from `status`, never translated label text.

Progress item statuses:

| Status | UI treatment |
| --- | --- |
| `PENDING` | Grey inactive ring and muted label |
| `RUNNING` | Blue spinner and active label |
| `COMPLETED` | Blue checked circle |
| `FAILED` | Error icon and error styling |
| `CANCELLED` | Cancelled/inactive styling |

Job status handling:

| Job status | Frontend action |
| --- | --- |
| `QUEUED` | Render `stage` (it may say waiting for provider capacity or retrying); keep the stream open or poll in fallback mode |
| `RUNNING` | Render `current_phase` and keep receiving progress |
| `STRUCTURE_READY` | Show Preparing course details and keep receiving progress |
| `COMPLETED` | Stop polling and navigate to the course builder |
| `FAILED` | Stop polling and show retry/back actions |
| `CANCELLED` | Stop polling and return to the initial form |

When `builder_ready` becomes `true`, the outline exists, but the frontend must
not navigate until `status` is `COMPLETED`; scripts and assessments may still
be in progress.

## 3. Retry a failed generation

`POST /api/v1/course-ai-generations/{job_id}/retry/`

Use this for a `FAILED` or `CANCELLED` job. The backend reuses completed
modules, lessons, and assessments and queues the unfinished work. Retries are
bounded, and completed jobs cannot be retried.

## 4. Stop the process

The Figma button **Stop this process and go back** calls:

`DELETE /api/v1/course-ai-generations/{job_id}/`

The response is `202` with `cancel_requested: true`. If the job is still
`QUEUED`, the response is already `CANCELLED`; for a running job, disable the
button after the first click and keep listening/polling until the worker reaches
a safe checkpoint and reports `CANCELLED`. The provider request already in
flight cannot be interrupted; the worker checks the request immediately after
that call returns and before persisting its result or starting another provider
call. If full-course generation already created the draft outline, cancellation
leaves that partial draft available for the bounded retry flow. Discard the job
ID only after the terminal state is observed. Cancellation racing with final
completion is serialized, so either the job completes first or cancellation wins;
a completed job is not changed to cancelled.

## 5. Open the generated course

On `COMPLETED`, read the course UUID from either `course` or
`result.course_id`, then request:

`GET /api/v1/courses/{course_id}/`

The course detail response includes course information, nested modules, lesson
data, and the final assessment. Route the user to the existing Course
Information builder screen with this ID. AI output is an editable `DRAFT`; the
creator must review it, add the required cover video, and pass the normal
quality/submission flow.

Related builder endpoints are already available when a screen needs a focused
refresh:

- `GET /courses/{course_id}/modules/`
- `GET /courses/{course_id}/modules/{module_id}/`
- `GET /courses/{course_id}/modules/{module_id}/lessons/`
- `GET /courses/{course_id}/modules/{module_id}/lessons/{lesson_id}/`
- `GET /courses/{course_id}/modules/{module_id}/assessment/`
- `GET /courses/{course_id}/final-assessment/`

For the complete Course Builder field map and the Figma-aligned lesson, module,
and final quiz payloads, see
[Course Builder Frontend Integration Guide](COURSE_BUILDER_FRONTEND_INTEGRATION.md).

## Recommended TypeScript types

```ts
type GenerationPhase = "CREATING_CONTENT" | "PREPARING_DETAILS";
type GenerationStatus =
  | "QUEUED"
  | "RUNNING"
  | "STRUCTURE_READY"
  | "COMPLETED"
  | "FAILED"
  | "CANCELLED";
type GenerationItemStatus =
  | "PENDING"
  | "RUNNING"
  | "COMPLETED"
  | "FAILED"
  | "CANCELLED";

interface GenerationItem {
  id: string;
  key: string;
  label: string;
  phase: GenerationPhase;
  status: GenerationItemStatus;
  order: number;
  error_message: string;
}

interface GenerationJob {
  id: string;
  course: string | null;
  kind: "FULL_COURSE";
  status: GenerationStatus;
  stage: string;
  current_phase: GenerationPhase;
  result: { course_id?: string; builder_ready?: boolean };
  error_message: string;
  cancel_requested: boolean;
  builder_ready: boolean;
  items: GenerationItem[];
  created_datetime: string;
  updated_datetime: string;
}
```

## Polling example

```ts
const POLL_INTERVAL_MS = 2_000;

async function waitForGeneration(jobId: string, signal: AbortSignal) {
  while (!signal.aborted) {
    const job = await api.get<GenerationJob>(
      `/course-ai-generations/${jobId}/`,
      { signal },
    );

    renderPhase(
      job.current_phase,
      job.items
        .filter((item) => item.phase === job.current_phase)
        .sort((a, b) => a.order - b.order),
    );

    if (job.status === "COMPLETED") {
      const courseId = job.course ?? job.result.course_id;
      if (!courseId) throw new Error("Completed job has no course ID");
      router.replace(`/creator/courses/${courseId}/information`);
      return;
    }
    if (job.status === "FAILED") {
      showGenerationError(job.error_message || "Course generation failed.");
      return;
    }
    if (job.status === "CANCELLED") {
      router.replace("/creator/courses/create-with-ai");
      return;
    }

    await new Promise((resolve) => setTimeout(resolve, POLL_INTERVAL_MS));
  }
}
```

Use an `AbortController` to stop polling when the component unmounts. Guard
against overlapping timers, retry transient network failures with bounded
backoff, and treat `401` as a session-refresh/login concern rather than a
generation failure.

## Error and retry behavior

- `400`: show field errors on the initial form. Common cases are missing
  `title`, unaccepted terms, or a topic outside the selected category.
- `401`: refresh the access token or route to login.
- `403`: the account is authenticated but is not a Course Creator.
- `404` while opening the stream or polling: the job does not exist or belongs to another creator.
- `429` when starting a generation, assist, or thumbnail: the creator already
  has an active AI job. Call `GET /course-ai-generations/`, continue polling
  the returned job, and only start another after it reaches `COMPLETED`,
  `FAILED`, or `CANCELLED`.
- `503` when starting a generation: the backend could not hand the job to
  Celery. The job is marked `FAILED`; show the error and allow a fresh retry.
- `FAILED` job: display `error_message`; starting again should use a new
  idempotency key because the old key intentionally resolves to the failed job.
- Stale in-progress jobs are marked `FAILED` by the backend before list or
  poll responses are returned, so the UI should stop polling when it sees that
  terminal state.
- Network timeout while polling: keep the same job ID and retry the GET. Never
  create a second job merely because a poll failed.

## Acceptance checklist for the frontend

- The form sends `title`, not the deprecated `course_title` alias.
- Category selection clears an incompatible topic selection.
- One idempotency key is stable for one form submission.
- Refreshing either loading screen first calls `GET /course-ai-generations/`,
  then falls back to the stored job ID if needed.
- Only the three items for `current_phase` are rendered.
- Checklist icons are derived from item status.
- The stop button calls DELETE once and waits for `CANCELLED`.
- Navigation occurs only after `COMPLETED`.
- The builder loads `course`/`result.course_id` from the completed job.
- Failed and cancelled jobs do not enter the builder automatically.
